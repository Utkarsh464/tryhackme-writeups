# Logs Fundamentals - Concepts

## Windows Event Logs
Windows maintains three primary event logs. The Application log records events from applications and services, including errors from malfunctioning software and informational events from properly functioning applications. The System log records events from Windows system components, including driver failures, service start/stops, and hardware issues. The Security log records audit events including authentication attempts (logon/logoff), object access (file, registry, directory), privilege use, account management (creation, modification, deletion), and process tracking. The Security log is most relevant for security investigations. Each event includes: a unique Event ID representing the type of event, a timestamp in UTC or local time with timezone offset, a source (the software that logged the event), a level (Information, Warning, Error, Critical, Verbose), and a user and computer name associated with the event. The detailed XML view provides the complete event data, including parameter-specific values.

## Linux System Logs
Linux stores logs primarily in the /var/log directory. Key log files include: syslog (or messages on some distributions), which contains most general system messages excluding authentication-related events; auth.log (or secure on RedHat-based systems), which contains authentication events including SSH logins, sudo commands, and user account changes; kern.log, which contains kernel messages and driver events; dmesg, which is the kernel ring buffer containing boot-time messages and hardware detection; apt/history.log (Debian-based), which records package installations and upgrades; apache2/access.log and error.log (or httpd on RedHat-based systems), which record web server access and errors; and mail.log, which records email server activity. Modern Linux distributions use systemd-journald for structured, binary logging accessible via journalctl. The journal retains metadata that is not available in traditional text logs, including kernel facility, priority, and structured data fields. Journals can be forwarded to traditional syslog for centralization.

## Log Formats and Structure
Log entries follow various formats depending on the source. Syslog format (RFC 5424) includes: timestamp, hostname, application name, process ID, and message. Common Log Format (CLF) for web servers includes: remote host, identd, auth user, timestamp, request line, status code, and response size. Windows EVTX format is binary but when exported appears as structured XML with specific fields for each event type. Modern applications increasingly use JSON-structured logs, which are machine-parseable and support nested data structures. Understanding log formats is essential for writing accurate parsing rules and for correctly interpreting log entries during investigations.

## Log Levels and Severity
Every log entry has a severity level that indicates its urgency and importance. Standard syslog severity levels (0-7) are: Emergency (system unusable), Alert (immediate action required), Critical (critical conditions), Error (error conditions), Warning (warning conditions), Notice (normal but significant condition), Informational (informational messages), and Debug (debug-level messages). In practice, most security-relevant information appears at Notice, Warning, or Error levels. Log level usage varies between applications, so understanding the specific logging conventions of each system is important. Event logs should be filtered by appropriate severity levels to avoid information overload while ensuring critical events are not missed.

## Timestamp Analysis and Time Zones
Timestamps are critical for reconstructing attack timelines, but they must be handled carefully. Logs may use different time zones (UTC vs local time), different formats (ISO 8601, epoch time, human-readable), and may be affected by system clock drift or deliberate tampering. Security analysts must normalize timestamps to a common reference (typically UTC) when correlating events across multiple systems. The NTP service is critical for ensuring consistent time across all systems. Timestamp anomalies (impossible sequences, inconsistent time zones) can themselves be indicators of log manipulation or anti-forensic activity.

## Log Collection and Centralization
Centralized log collection aggregates logs from multiple systems into a central repository for analysis, retention, and correlation. Syslog is the standard protocol for Linux log forwarding, with rsyslog and syslog-ng as common implementations. Windows Event Forwarding (WEF) and Windows Event Collector (WEC) provide Windows-native log collection. Agents from SIEM platforms (Splunk Universal Forwarder, Elastic Beats, Fluentd) collect logs from various sources and forward them to the central platform. Centralized logging provides several security benefits: logs are protected from tampering by attackers who compromise individual systems, correlation across systems enables detection of multi-host attack patterns, and centralized storage enables long-term retention and compliance with regulatory requirements.
